# API contracts

EZTest treats an API's contract as something every run checks, not a separate tool. This page covers:

- importing OpenAPI and Postman assets as journeys;
- validating every API step against the spec;
- API coverage;
- spec lint rules;
- mocks generated from a spec;
- EZTest consumer-driven contracts, from the consumer journey to `can-release`;
- OAuth for API steps, GraphQL schema validation and subscriptions, and WebSocket connections with headers and certificates.

Everything is deterministic and runs locally. Nothing is generated by an AI model.

## Import OpenAPI, Swagger and Postman

```bash
eztest import specs/shop.yaml --kind openapi --role api -o journeys/api
eztest import shop.postman_collection.json --postman-env shop.postman_environment.json -o journeys/postman
```

Both formats are also detected from the file content, so `--kind` is optional.

### OpenAPI 3.0 / 3.1 and Swagger 2.0

You get one journey per tag (or `groupBy: 'operation'` from code). Within each journey:

- Operations run in create, read, update, delete order.
- A path such as `/orders/{id}` reuses the id that the `POST /orders` step returned (`${createOrder.body.id}`).
- Path, required query and header parameters, and request bodies come from the spec's examples. Where there is no example, a seeded generator makes the values, so the same spec always gives the same journeys.
- Secured operations run `as <role>` when you pass `--role`. Otherwise the journey has a comment that says which credentials are needed.

Each operation becomes a step plus two expectations:

```text
Call API "GET /api/orders/1" as api and store as getOrder
  Expect response getOrder status is 200
  Expect response getOrder conforms to OpenAPI "specs/shop.yaml"
```

The spec's `servers` are listed in a comment. The run uses `baseUrl` from the config, so the same journeys work in every environment.

### Postman Collection v2.0 / v2.1

You get one journey per top-level folder.

**Requests:**

- `{{var}}` becomes `${var}`.
- Postman dynamic variables are rewritten: `{{$guid}}` becomes `${uuid()}` and `{{$timestamp}}` becomes `${now()}`.
- Folder and collection auth is inherited. Bearer and API-key auth become headers that reference variables (`Bearer ${token}`). Literal secrets in the collection are never copied.
- Raw, urlencoded, form-data and GraphQL bodies are supported.

**Test scripts.** These common `pm.*` assertions are converted:

| Postman test | EZ line |
|---|---|
| `pm.response.to.have.status(200)` | `Expect response x status is 200` |
| `pm.expect(jsonData.a.b).to.eql("v")` | `Expect response x "$.a.b" equals "v"` |
| `pm.expect(jsonData.a).to.include("v")` | `Expect response x "$.a" contains "v"` |
| `pm.expect(jsonData.a).to.exist` | `Expect response x has "$.a"` |
| `pm.expect(pm.response.responseTime).to.be.below(500)` | `Expect response x responded within 500 ms` |
| `pm.environment.set("id", jsonData.id)` | `Capture "$.id" from x as id` |

A request whose tests expect a 4xx or 5xx status is sent `with errors allowed`.

**Environment files.** Non-secret values of the environment file become the `Variables:` header. Secret values (and keys that look like passwords or tokens) are listed by name in a comment. Set them from `secret://` references.

**Not converted.** Everything else, including pre-request scripts, becomes a `# TODO (not converted): ...` line in the journey and in the import report. Nothing is dropped silently.

## Validate every API step against the spec

```yaml
api:
  spec: specs/shop.yaml        # or a list: [specs/shop.yaml, { file: specs/partner.yaml, baseUrl: https://partner.example/v2 }]
  specMode: enforce            # enforce (default) | warn
  specStrict: false            # also fail calls that match no operation
```

With `api.spec` set, every REST API step is matched to an operation. The most specific path template wins: `/orders/special` beats `/orders/{id}`. Server base paths such as `/v1` are stripped before matching. A spec given as `{ file, baseUrl }` checks only the calls under that base URL, so calls to other services (an OAuth token endpoint, another app) are neither validated against it nor counted in its coverage.

A request the spec calls invalid that the server refuses with a 4xx response is a passing negative test, not a violation; it is recorded as `refusedInvalidRequest`.

EZTest validates the request and the response.

**Request:**

- path, query and header parameter schemas;
- required parameters;
- the request body schema.

**Response:**

- the documented status (exact, `2XX`, then `default`);
- required response headers and their schemas;
- the content type;
- the body schema.

A break fails the step. The message names the JSON pointer:

```text
GET /api/orders/1 -> 200 breaks the API contract (getOrder): response /created_by: required property is missing
```

Every validated call is also stored as contract evidence (`contracts/<journey>/<step>.json`). That evidence includes the operation, the status, the violations and the request header names (never the values).

### Spec support

| Feature | Details |
|---|---|
| `$ref` | Local and relative-file refs (`common.yaml#/Money`) are resolved and cyclic schemas work. Remote (`http:`) refs are refused: download them next to the spec. |
| OpenAPI 3.0 schema keywords | `nullable` and boolean `exclusiveMinimum`/`exclusiveMaximum` are translated to JSON Schema. |
| OpenAPI 3.1 | JSON Schema 2020-12 with type arrays and `$ref` siblings. |
| Swagger 2.0 | `basePath`, `body` and `formData` parameters, `produces`/`consumes`. |
| Formats | ajv-formats, plus `int32`, `int64`, `float`, `double` and `byte`. |

To check one response explicitly, use one of these:

```text
Expect response order conforms to OpenAPI "specs/shop.yaml"
Expect response order conforms to the API spec operation "getOrder"
```

The second form uses `api.spec`. It also works for a value that was not captured by an API step.

## API coverage

After a run with `api.spec`, EZTest writes `api-coverage.json` and `api-coverage.md` into the run directory and records them in the evidence chain. The coverage covers:

- **Operations** exercised out of those in the spec.
- **Status codes:** the documented codes that were seen, the missing ones, and statuses the spec does not document.
- **Parameters** exercised: path, query, header and body.
- **Calls not described by the spec.**
- **Contract violations** per operation.

The coverage appears in four places:

| Where | How |
|---|---|
| HTML and JSON reports | An "API coverage" section. |
| Studio | **Project › API contracts**, per run, with a trend across runs. |
| CLI | `eztest contracts coverage <runDir> [--spec x] [--min 0.8]` (exit 1 below `--min`). |
| Readiness gate | `apiCoverage` (see below). |

```text
| | Covered | Total | Ratio |
| Operations | 4 | 5 | 80% |
| Status codes | 5 | 11 | 45.5% |
...
| **untested** `GET /api/orders/{id}` (getOrder) | 0 | - | 200, 401, 404 | - | path:id |
```

## Spec lint (governance)

`eztest contracts lint specs/shop.yaml [--rule operation-tags=off] [--json]` exits 1 when a rule of severity error fails. The rules:

| Rule | Severity | What it checks |
|---|---|---|
| `info-title-version` | error | `info.title` and `info.version` are set |
| `servers-defined` | warning | the spec declares servers (or host and basePath) |
| `operation-id` | error | every operation has an operationId |
| `operation-id-unique` | error | operationIds are unique |
| `operation-summary` | warning | every operation has a summary or description |
| `operation-tags` | info | every operation has tags |
| `success-response` | error | every operation documents a 2xx or 3xx response |
| `error-response` | warning | every operation documents a 4xx or default response |
| `response-schema` | warning | JSON responses have a schema |
| `path-params-declared` | error | path parameters match the path template |
| `security-defined` | error | security requirements name declared schemes |
| `no-trailing-slash` | warning | no path ends with `/` |
| `get-no-body` | error | GET and HEAD operations have no request body |
| `request-body-example` | info | request bodies have examples (used by imports and mocks) |
| `unresolved-refs` | error | every `$ref` resolves |

## Mocks from a spec

```bash
eztest mock from-openapi specs/shop.yaml --port 4710 --seed 42
eztest mock from-openapi specs/shop.yaml --store mocks/shop.json   # an eztest mock store instead
```

Each request is matched to an operation and validated against the spec. An invalid request gets `400` with the rule it broke:

```json
{ "error": "invalid_request", "operation": "quote", "violations": [{ "rule": "body", "at": "/qty", "message": "/qty: must be >= 1" }] }
```

The response is the spec's example. Without one, data is generated from the response schema with a seeded generator. The generator respects:

- enums, formats, numeric bounds and string lengths;
- simple patterns such as `^SKU-\d+$`;
- property-name hints such as `email`, `name` and `city`.

The same request always gets the same body, and the body is valid against the schema. To get another documented response, send `Prefer: code=404` or add `?__code=404`.

From code, use `createOpenApiMock({ spec, seed })` and `mockStoreFromSpec(spec)`.

## EZTest contracts: consumer-driven contracts

An EZTest contract says what a consumer application relies on from a provider API. A consumer journey records it, the provider verifies it against a running instance, and the EZTest results server (`eztest server`) keeps every published contract, every verification result and what is released where, so `eztest contracts can-release` can answer whether a version is safe to release.

### Consumer side: a journey records the contract

```text
Journey: Shop web consumer
Start a contract between consumer "shop-web" and provider "orders-api"
Call API "POST /api/public/quote" with body '{"sku":"SKU-200","qty":2}' and store as quote
Given provider state "order 1 exists" with total=99
Call API "GET /api/orders/1" as api and store as order
  Expect response order "$.lines[0].sku" equals "SKU-200"
Finish the contract
```

Every API step in the session becomes an expectation: the request, the provider state it needs, and the response the consumer saw, with matchers.

**What the file contains.** `Finish the contract` writes (or merges into) `contracts/shop-web-orders-api.contract.json`:

- Expectations with the same description and provider states are replaced, so re-running a journey updates its contract.
- A journey that fails before `Finish the contract` writes nothing, so a contract only records behaviour a passing journey saw.
- Request credentials never reach the file. Only `Content-Type` and `Accept` request headers are kept, and all text goes through the secret masker.

### The contract file

Contract files are JSON or YAML (`*.contract.json`, `*.contract.yaml`, `*.contract.yml`) and can be written by hand:

```yaml
format: eztest-contract
version: 1
consumer: shop-web
provider: orders-api
expectations:
  - description: Get order 1
    given: [{ state: order 1 exists, params: { total: 99 } }]
    request: { method: GET, path: /api/orders/1, headers: { accept: application/json } }
    response:
      status: 200
      headers: { content-type: application/json }
      body: { id: 1, status: Submitted, lines: [{ sku: SKU-200, qty: 2 }] }
      match:
        $.id: integer                              # a matcher kind ...
        $.lines: { kind: type, min: 1 }            # ... or a matcher with options
        $.lines[*].sku: { kind: regex, regex: "^SKU-\\d+$" }
        $.status: { any: [{ kind: regex, regex: "^Submitted$" }, { kind: regex, regex: "^Paid$" }] }
      headerMatch:
        x-request-id: { kind: regex, regex: "^[0-9a-f-]{36}$" }
```

Matcher kinds: `type`, `regex`, `equality`, `include`, `integer`, `number`, `boolean`, `null`, `date`, `time`, `timestamp`, `eachValue` (every value of an object like the first), `notEmpty` and `semver`. A list of matchers must all hold; `{ any: [...] }` needs one. Without a matcher a value must be equal; a `type` matcher on an object or array cascades to everything below it. Response bodies may have extra keys; a missing key fails.

**Matchers are inferred** from what was recorded:

| `contracts.matchers` | Matchers |
|---|---|
| `type` (default) | Every leaf is a type match. Every non-empty array is "at least one like the first". |
| `schema` | Uses the response schema in `api.spec`: integers, numbers and booleans, enums as regexes, patterns, and `date`, `date-time` and `uuid` formats. |
| `exact` | None: values must be equal. |

`eztest contracts from-mocks --store mocks/shop.json --consumer web --provider shop` writes a contract from an `eztest mock` recording.

### Message contracts

Inside a contract session, every message a wait receives (`Wait for a message on Kafka topic "invoices" ...`, on Kafka, RabbitMQ/AMQP, MQTT or IBM MQ) becomes a message expectation, with matchers inferred from the payload:

```yaml
  - kind: message
    description: Wait for a message on Kafka topic "invoices" where "$.orderId" = 7 as invoice
    channel: { transport: kafka, destType: topic, dest: invoices }   # kafka | amqp | mqtt | ibmmq | memory
    message:
      contents: { invoiceId: INV-7, orderId: 7 }
      contentType: application/json
      match: { $.invoiceId: type, $.orderId: type }
      # key: "7"                         # optional: the Kafka key / AMQP routing key the consumer relies on
      # headers: { type: invoice.created }  # optional, with headerMatch for patterns
```

The provider side makes the provider publish each message and reads it from its broker on the expectation's channel:

```yaml
contracts:
  provider:
    messageProducers:
      "invoice created": { broker: bus, trigger: "POST /api/orders", body: { sku: SKU-1 } }   # by expectation description
      "*": { timeoutMs: 15000 }        # any other message: wait for the provider to publish it on its own
```

Each entry may override `dest` and `destType`. A message expectation without a producer fails verification (it is never skipped), and `can-release` covers message expectations like HTTP ones, because verification results are recorded against the whole contract's hash. From code, pass `messageProducers` to `verifyContract`.

### Provider side: verify against a running provider

```yaml
contracts:
  provider:
    name: orders-api
    baseUrl: http://localhost:8080
    asRole: api                    # bearer token from the Identity Vault for replayed requests
    states:
      "order 1 exists":
        sql: "INSERT INTO orders (id, total) VALUES (1, $${total})"   # $${..} = a state param, not a config variable
        on: shop
        teardown: { sql: "DELETE FROM orders WHERE id = 1", on: shop }
      "a customer":    { query: SEED_CUSTOMER, on: shop, with: { name: "$${name}" } }   # named query (db.queries)
      "stock is low":  { request: "POST /test/stock", body: { sku: "SKU-1", qty: 1 } }   # HTTP setup call on the provider
      "user logged in": { journey: seed-user }                                       # run a journey with the params as variables
    stateChangeUrl: http://localhost:8080/_test/state   # fallback for states without a hook: POST { state, params, action }
```

```bash
eztest contracts verify contracts --provider orders-api                        # local contract files
eztest contracts verify --provider-version $SHA --consumer-branch main --publish  # contracts from the results server, results recorded there
eztest contracts verify --provider-version $SHA --environment production --publish  # the consumers released to production
eztest contracts verify contracts --run eztest-results/<runId>                 # record the result for the readiness gate
```

**How each expectation is verified:**

1. EZTest puts the provider into the expectation's states with your data hooks. These run as setup, and the `teardown` part runs afterwards.
2. It replays the request.
3. It compares the response under the contract's matchers, naming the path of every mismatch: `body $.created_by: is missing`.

Without `--consumer-branch` or `--environment`, `verify` fetches the latest contract of each consumer plus every contract a released consumer version published. Contracts with the same content are verified once.

### Publishing, releases and can-release (EZTest results server)

```yaml
server: { url: https://eztest.example.com, project: shop }   # token: EZTEST_SERVER_TOKEN, or server.token
contracts:
  app: shop-web                    # this application on the results server
  branch: main
  canRelease: { environment: production }
```

```bash
eztest contracts publish --app-version $SHA                                     # contract files of contracts.dir, for this consumer version and branch
eztest contracts can-release --app-version $SHA --environment production --run eztest-results/<runId>
eztest contracts record-release --app orders-api --app-version 2.0.0 --environment production
```

- **publish** stores each contract for the consumer version and branch. Publishing the same content again is a no-op; different content for a version that is already published is refused.
- **verify --publish** records each result against the contract's content hash and the provider version, so a consumer version that publishes unchanged content is already verified.
- **record-release** records which version of an application is now in an environment (the deployment step of your pipeline). It needs the `contracts.release` permission (role `approver` or `admin`).
- **can-release** answers yes only when every contract check passes. As a consumer, every contract the version published must have been verified, and passed, by the provider version released to that environment. As a provider, every consumer released to that environment must have been verified, and passed, by this version. A provider with nothing released to the environment, or a contract nobody verified, is a no with that reason. It exits 1 unless the answer is yes; with `--run` the answer is recorded in the run as evidence for the readiness gate.

The server API (all under `/api/projects/<project>/`, with an API token: `tester` to publish contracts and verification results, `approver` (the `contracts.release` permission, the release manager's role) to record releases, `viewer` to read): `POST|GET contracts`, `GET contracts/<consumer>/<provider>/<version>`, `POST|GET verifications`, `POST|GET releases` and `GET can-release?app=&version=&environment=`. Every write is in the audit log (`contract.publish`, `contract.verify`, `contract.release`).

## Readiness gates

```yaml
gates:
  apiCoverage: { minOperations: 0.8, minStatusCodes: 0.5, noViolations: true }   # or apiCoverage: 0.8
  contracts: true      # contract verification passed and can-release said yes (blocker by default)
```

`apiCoverage` reads the run's `api-coverage.json`. `contracts` reads `contracts-results.json`, which `eztest contracts verify --run` and `can-release --run` write. Both gates cite the evidence ids of those files. Without data, a gate reports missing input rather than passing.

## OAuth for API steps

`Call API "GET /api/orders" as alice ...` sends `Authorization: Bearer <token>` with the token of the role's `api:` block (configuration.md, "Identity: OAuth for API steps"). The grants are client credentials, resource-owner password, authorization code with PKCE (EZTest's own headless browser signs in on the identity provider's form as the role, and the redirect is intercepted), device code (approved in the browser as the role), JWT bearer and a stored refresh token. Clients authenticate with a secret (basic or post), `private_key_jwt` or not at all. Tokens are cached per role and refreshed with the refresh token the server returned; a refused refresh signs in again.

Proven against a local OAuth / OpenID Connect server written for the tests (`test/server/mock-oidc.ts`), which checks PKCE, client assertions (signature, audience, replay), the device-code polling rules and refresh-token rotation (`test/identity/oauth-grants.test.ts`).

## GraphQL: schema validation and subscriptions

```text
Validate GraphQL query "query ($id: ID!) { order(id: $id) { id status total } }" against the schema of /graphql as manager
Introspect the GraphQL schema at /graphql and store it as schema
Subscribe to GraphQL "subscription ($id: ID!) { orderUpdated(id: $id) { status } }" at /graphql as updates using role manager with variables '{"id":"7"}'
Wait for a GraphQL event on updates where "$.data.orderUpdated.status" = "SHIPPED" within 10 s and store it as shipped
Stop GraphQL subscription updates
```

- **Validation** introspects the server once and checks the document with EZTest's own GraphQL parser and validator: fields on the right types (with suggestions), union selections, leaf and object selections, arguments (unknown, missing, repeated) and literal values (Int range, enum values, input objects), fragments (unknown, unused, cycles, impossible spreads), variables (undefined, unused, output types, nullable passed where a value is required), directives and operations (one root field per subscription). Every problem has its line:column; the step lists them all. A server with introspection disabled is reported as such.
- **Subscriptions** use the graphql-transport-ws protocol on EZTest's own WebSocket client: `connection_init` (carrying the role's `authorization`, which is also sent as a handshake header), `connection_ack`, `subscribe`, `next` / `error` / `complete`, ping / pong. Events are buffered from the subscribe step on, so a wait sees events that came first. A refused `connection_init` (close code 4403) fails the step as forbidden.
- **SDK**: `graphql.query`, `graphql.validate`, `graphql.introspect`, `graphql.subscribe(...).next(where).stop()` from `@mohammed-a-khan/eztest/sdk` (also `ctx.graphql`); programmatically, `GraphQLClient.introspect()` / `.validate()`, `validateGraphQL(document, schema)` and `GraphQLWsClient` from `@mohammed-a-khan/eztest/surfaces`.
- Not covered: the older `subscriptions-transport-ws` protocol, and validation rules that need execution semantics (overlapping field merging, `@defer` / `@stream`).

## WebSocket with headers and certificates

`Connect to websocket "/quotes" as feed using role trader with headers "X-Tenant" = "eu" with protocol "quotes.v1" with ping every 15 s` opens a WebSocket on EZTest's own RFC 6455 client (the browser driver's, extended): handshake headers (the role's bearer token, cookies, any header), subprotocols (the server must pick an offered one), a client certificate for `wss://` (`with client certificate "partner"` from `api.clientCertificates`), the environment's proxy (HTTPS_PROXY / NO_PROXY, a CONNECT tunnel), binary messages, pings both ways and a keep-alive that closes a connection whose server stopped answering. Load tests (`ws` actions) use the same client.

## Limits

- Postman Collection v3 (YAML, git-native format) is not imported yet; export v2.1 JSON.
- `readOnly` and `writeOnly` are not applied per direction when validating, so a required `writeOnly` property is required in responses too.
- Contract files are EZTest's own format. Files in other tools' contract formats are not read; `eztest contracts verify` says so.
